# SmartRelay (C# / Windows)

Локальное управление розеткой SmartLife / Tuya **без интернета** — прямо по локальной сети (LAN).

Поддерживаются протоколы **3.1** и **3.4** (поле `ver` в конфиге). Все кадры собираются
по эталонной схеме `tinytuya` (big-endian заголовок `>4I`, AES-128-ECB, HMAC-SHA256 / CRC32).

**Версия:** 5.0.0 (19.11.2026) · **Лицензия:** MIT (`LICENSE`)
**Архитектор:** avk013 · **Исполнитель:** Cline (AI coding agent) mokoki

Эти сведения зашиты в программу (`AppInfo.cs`), видны в окне «О программе», в заголовке
журнала и по команде `SmartRelay.exe --version`; при необходимости переопределяются
в `smartrelay.json` (`architect` / `executor`).

## Что нужно

- .NET 7+ Runtime или опубликованный `SmartRelay.exe`
- Device ID розетки (gwId / devId, обычно 20 символов)
- Local Key (ключ локального доступа, 16 символов или 32 hex-символа)
- IP-адрес розетки в вашей Wi-Fi сети

**Важно:** Local Key нужно получить один раз (через портал разработчиков Tuya, резервную
копию приложения SmartLife или перехват трафика). После этого программа работает автономно.

## Режимы работы

### 1. Графический интерфейс (по умолчанию)

`SmartRelay.exe` — окно с кнопками:

- **Строка «Состояние: ВКЛ / ВЫКЛ»** — реальное состояние розетки с самого устройства
- **ВКЛ / ВЫКЛ** — включают и выключают реле (надписи из `smartrelay.json`);
  активная кнопка подсвечивается ярко, неактивная — приглушённо
- **Диагностика (журнал)** — открывает окно с живым журналом: проверка TCP-портов,
  UDP-обнаружение устройства, попытки рукопожатия 3.4 и 3.1, hex-дампы кадров.
  Кнопку можно скрыть в конфиге: `"showDiag": false`
- **Внизу окна** — ссылка `v5.0.0 · MIT · О программе…`: версия, дата выпуска, лицензия,
  архитектор и исполнитель (текст можно скопировать или открыть файл `LICENSE`)

Версия также видна в заголовке окна и в свойствах файла `SmartRelay.exe` (Проводник →
Свойства → Подробно), так что запутаться в разных сборках не получится.

Состояние обновляется автоматически каждые 3 секунды (`"poll"` в конфиге, `0` — только
по нажатию кнопок). Каждый опрос — **один пакетный запрос** `0x10` (`DP_QUERY_NEW` для 3.4)
или `0x0A` (для 3.1), в ответ приходят сразу все DP; TCP-соединение при этом не
переоткрывается. Поэтому в окне видно и переключение из приложения SmartLife,
и нажатие физической кнопки на розетке.

После команды ВКЛ/ВЫКЛ приложение проверяет результат: если прошивка отвечает только
подтверждением `{}` без состояния, автоматически отправляется запрос статуса в том же
соединении, и надпись показывает фактическое состояние, а не «на веру» отправленную команду.

### 2. Консольный режим (CLI)

```
SmartRelay.exe --id <DEVICE_ID> --key <LOCAL_KEY> --ip <IP> [--port 6668] on|off|status|toggle
SmartRelay.exe --id <DEVICE_ID> --key <LOCAL_KEY> --ip <IP> diag
```

`diag` — расширенная диагностика: печатает проверку портов, UDP-broadcast, результат
рукопожатия и полные hex-дампы отправленных/полученных кадров.

Все сообщения дублируются в файл `smartrelay.log` рядом с `SmartRelay.exe`
(на Linux/macOS — в каталоге сборки).

## Конфигурационный файл

Создайте `smartrelay.json` рядом с `SmartRelay.exe` — скопируйте шаблон `smartrelay.json.example`
(он лежит в корне репозитория и автоматически попадает в папку публикации вместе с `SmartRelay.exe`):

```json
{
  "dev_id": "0123456789abcdef0123",
  "local_key": "abcd1234efgh5678",
  "ip": "192.168.1.42",
  "port": 6668,
  "index": 1,
  "timeout": 5,
  "ver": "3.4",
  "poll": 3000,
  "showDiag": true,
  "architect": "avk013",
  "executor": "Cline (AI coding agent) mokoki",
  "btnOnText": "ВКЛ",
  "btnOffText": "ВЫКЛ"
}
```

| Поле | Описание |
|------|----------|
| `dev_id` | Device ID (gwId/devId) розетки |
| `local_key` | Local Key (16 символов или 32 hex) |
| `ip` | IP-адрес розетки в локальной сети |
| `port` | TCP порт, по умолчанию **6668** |
| `index` | Номер точки данных DP (по умолчанию 1) |
| `timeout` | Таймаут сети, сек (по умолчанию 5) |
| `ver` | Версия протокола: `"3.4"` (по умолчанию) или `"3.1"`; при ошибке версия подбирается автоматически |
| `poll` | Период автоопроса состояния в мс (по умолчанию 3000; `0` — опрос отключён) |
| `showDiag` | Показывать кнопку «Диагностика (журнал)»: `true` (по умолчанию) / `false` |
| `architect` | Архитектор решения (по умолчанию зашит `avk013`); выводится в окне «О программе» и в `--version` |
| `executor` | Исполнитель работ (по умолчанию зашит `Cline (AI coding agent) mokoki`) — там же |
| `btnOnText` | Надпись на кнопке ВКЛ |
| `btnOffText` | Надпись на кнопке ВЫКЛ |

Файл `smartrelay.json` не коммитится (`.gitignore`), чтобы не публиковать ваши ключи.

## Если приходит «Ответ не получен»

Запустите диагностику:

```
SmartRelay.exe diag            (с настройками из smartrelay.json)
```

Она по шагам покажет, что именно не так:

1. **Проверка TCP-портов** — пробует порт из конфига, затем 6668, 6667, 8886, 8887, 6666.
   Если открыт другой порт, в журнале будет явное предупреждение — укажите его в `"port"`.
   `connection refused` = устройство не слушает этот порт (или неверный IP).
2. **UDP-обнаружение** — широковещательный запрос на 6666/6667. Если розетка отвечает,
   в журнале появится её реальный `id`, `ver` и `productKey` — так можно проверить,
   что Device ID и версия протокола указаны верно.
3. **Рукопожатие** — пробует версию из конфига, затем альтернативную. Точные причины:
   - «на запрос 0x03 ответа нет» — порт/фаервол/устройство не в LAN-режиме;
   - «HMAC в ответе 0x04 не совпал» — **неверный Local Key**;
   - «не удалось расшифровать ответ 0x04» — тоже почти всегда неверный Local Key.
4. **Если handshake прошёл, а команда обрывается** («соединение закрыто»/«ответ не получен»
   сразу после успешного согласования ключа) — устройство расшифровало кадр, но не поняло
   payload: неверный сессионный ключ или неверный формат команды/JSON для этой версии.
   В журнале (`--verbose`) видно отправленный JSON и ответ устройства.

### Версия протокола определяется автоматически

`"ver"` в конфиге — только первый вариант. Если с ним связи нет, программа сама пробует
другую версию (3.4 ↔ 3.1): при обрыве во время операции один раз повторяет её, а при
неудачном handshake 3.4 — сразу переходит на 3.1. Если сработала «не та» версия, в журнале
появится строка вида:

```
ВНИМАНИЕ: устройство работает по протоколу 3.4, а в конфиге указано 3.1.
Исправьте "ver": "3.4" в smartrelay.json.
```

Работать будет и с неверным `ver`, но исправить конфиг стоит — иначе при каждом
подключении тратится одна лишняя неудачная попытка. Диагностика (`diag`) этот автоподбор
отключает и проверяет версии строго по одной, чтобы было видно реальный результат каждой.

### Что попадает в журнал (можно ли его пересылать)

Local Key в журнал **не пишется** — ни в конфиге, ни в дампах:

- в отчёте `diag` строка `Local Key: 16 байт (скрыт)`, Device ID маскируется (`0123…cdef`);
- hex-дампы кадров содержат только шифртекст, `HMAC-SHA256`, CRC32 и сессионный ключ;
- из сессионного ключа Local Key не вычисляется: это `AES(localKey, nonce1 XOR nonce2)`,
  а сами nonce'ы видны в дампе открытым текстом — но восстановить по паре «открытый
  текст → шифртекст» ключ AES нельзя. К тому же сессионный ключ живёт одно TCP-соединение;
- payload в 3.1/3.4 зашифрован, поэтому Device ID и содержимое JSON в дампе тоже не видны.

Единственное, что в журнале есть в открытом виде — IP-адрес розетки и частично Device ID.
Если не хотите показывать и это, замените IP в тексте журнала перед отправкой.

### Про порт 8886

Стандартный LAN-порт Tuya — **6668**. Порт 8886 у розеток Tuya обычно не используется,
поэтому если telnet на 8886 открывается, это, скорее всего, другое устройство/сервис
(роутер, камера и т.п.). Проверьте именно `telnet <IP> 6668` — успешное TCP-соединение
означает, что порт открыт, но само по себе не подтверждает, что это Tuya-протокол.
Если у вашего устройства действительно нестандартный порт, укажите его в `"port"` —
программа автоматически проверит и его.

## Протокол

### 3.1
Кадр `55AA`, AES-128-ECB, payload в base64 с MD5-сигнатурой (`3.1` + 16 hex + base64), CRC32 в конце.

### 3.4
1. `0x03 SESS_KEY_NEG_START` — сырые 16 байт локального nonce, AES/HMAC исходным Local Key.
2. `0x04 SESS_KEY_NEG_RESP` — 16 байт nonce устройства + HMAC-SHA256(localKey, localNonce);
   HMAC проверяется.
3. `0x05 SESS_KEY_NEG_FINISH` — HMAC-SHA256(localKey, remoteNonce).
4. Сессионный ключ = **AES-128-ECB без паддинга(localKey, `localNonce XOR remoteNonce`)**.
   Голый XOR ключом **не является** — это отдельный шаг шифрования.
5. Команды в 3.4 — «новые» (как в `tinytuya`), а не 0x07/0x0A:
   - включение/выключение: `0x0D CONTROL_NEW`, JSON `{"protocol":5,"t":<unixtime>,"data":{"dps":{"1":true}}}`,
     внутрь шифрования добавляется 15-байтовый заголовок `"3.4" + 12 нулей`;
   - запрос статуса: `0x10 DP_QUERY_NEW`, JSON `{}` **без** заголовка версии.
6. Ответы устройства содержат 4-байтовый `retcode` и приходят зашифрованными сессионным
   ключом; заголовок версии в ответе может как присутствовать, так и отсутствовать —
   разбор устойчив к обоим вариантам.

Критично: **handshake и команды идут в одном TCP-соединении** — сессионный ключ привязан
к соединению. Клиент держит постоянный сокет и переподключается только после ошибки.

Весь код на чистом C#, без внешних зависимостей.
